# 0005 — Catalog enrichment from declared software.yml fields

**Status:** accepted · **Date:** 2026-10-29 · **Fire:** #116 (records the #110–#115 pattern) · **Seeds:** D06 (install modes), D07 (runtime deps), D11/D14/D15 (provenance + deprecation), C12 (plan review), U13 (recommendations)

## Context

The App Store (Phase 4) and the plan review (intended-experience step 5) present the software.yml catalog — the ONE authoritative software list (D01/D13), already served read-only via `/api/catalog` + `/api/catalog/:name` and bundled as `catalog.json` (generated by `gen-catalog.mjs`, which reuses the canonical cnf index builder; no second catalog).

software.yml carries many declared `_`-prefixed metadata fields beyond the install providers: `_short` (description), `_github`/`_home`/`_docs` (provenance + links), `_app`/`_service` (GUI-app / service markers), `_deprecated` (a maintainer reason, often naming a replacement), `_deps` (runtime dependencies), plus internal ones (`_post`/`_pre` hooks, `_groups` OS groups, `_env`, `_when`, `_notes`).

The question across fires #110–#115: HOW to surface this metadata so a user can make an informed choice (what installs eagerly, what's deprecated, what it depends on) — WITHOUT inventing data a provisioning catalog must never fabricate.

## Decision

Enrich the catalog ONLY from EXPLICIT declared software.yml fields, merged at BUILD time in `gen-catalog.mjs` into the bundled `catalog.json`, carried through the `/api/catalog(/:name)` contract, rendered in the App Store, and INTERCONNECTED into the plan review (`/environment`) and Recommendations.

The recipe (now established, one merge point): add a field to the `gen-catalog.mjs` yq map → merge/derive it onto each catalog entry (filtering artifacts) → add it to the `CatalogEntry` type + the API response → render it in the App Store list/detail → interconnect it into any surface where it adds value → a failing-test-first `test-control-plane.sh` assertion.

Two hard rules govern the pattern:

1. **Explicit-declared only — never AI-generate or heuristically guess** user-facing catalog data. Ground every value in a real declared field.
2. **Measure viability BEFORE building.** For any field whose value drives a behaviour/grouping, measure its real distribution against the live catalog first; REJECT fields that don't genuinely differentiate or are internal. Reject-after-measurement is a win, not a failed fire.

Shipped under this decision: install-MODE badges (#110, `_app`/`_service` → app/service/cli), runtime DEPS (#113, `_deps`), DEPRECATION warnings on three surfaces — App Store badge (#112) · plan-review warning (#114) · actionable recommendation (#115) — plus the plan install-mode breakdown (#111) and the `?tenant=` plan deep-link (#114).

## Rationale

- software.yml is the single source of truth (D01). Deriving from it keeps the catalog honest and avoids a second, drifting metadata store.
- Build-time merge keeps the edge runtime free of YAML parsing (V01/V02) and makes the catalog a cacheable, bundled artifact.
- "Measure before building" repeatedly paid off (see Alternatives) — it turned three plausible-looking enrichments into correct REJECTIONS, avoiding churn that would have degraded accuracy.
- Interconnecting one declared signal across multiple surfaces (the App Store, the plan, the recommendations) multiplies its value for near-zero extra cost, since the derivation is already computed.

## Alternatives (considered and rejected)

- **AI-generate descriptions / install-modes / deprecation reasons.** Rejected: the non-user-facing `_desc` field is already AI-slop/hallucinated (corrected + gated at #96); a provisioning catalog must be grounded, not generated.
- **Treat `cask` presence as install-mode "app".** MEASURED-rejected (#110): of 40 cask-without-`_app` entries, most are CLIs shipped as casks (java/gcloud/flutter/fly/mitmproxy), so `cask→app` would mislabel MORE than it fixes. The explicit `_app`-only derivation is honest; a few GUI casks lacking `_app` fall to "cli" — an accepted, documented edge.
- **Surface `_groups` as "related tools".** MEASURED-rejected (#115): `_groups` are Unix/OS groups (`www-data`, `libvirt`, `sambausers`) a service needs, with 0 groups having ≥2 package members — a "related tools" feature would be degenerate.
- **Surface `_post` as "configure steps" (an R01 recipe stage).** Rejected (#115): `_post` values are raw multi-line shell scripts (internal provisioning hooks), not clean user-facing configuration steps; surfacing them raw would be noisy and confusing.
- **Maintain a separate curated catalog of metadata.** Rejected: violates the one-authoritative-catalog invariant (D01/D13); would drift from software.yml.

## Consequences

- The App Store + plan + recommendations surfaces are rich AND honest, grounded entirely in declared data; each enrichment ships with a failing-test-first assertion and (where renderable) live/real-browser verification.
- The high-value declared-field vein is now TAPPED (measured #115). Further enrichment requires NEW declared fields in software.yml, or a genuinely different capability (e.g. recipe-stage modelling), NOT more surfacing of the remaining low-value fields.
- This is NOT a hard one-way door — any single field-surfacing is reversible (remove the merge + render). The durable commitment is the PATTERN: derive-from-declared, measure-first, never-generate. A future contributor extends the catalog by following the recipe above, not by inventing data.
- `gen-catalog.mjs` is the single merge chokepoint; the `CatalogEntry` type is the single contract; the yq map is the single place a new field is declared. Low maintenance, hard to drift.
- The measured rejections (cask, groups, post) are recorded here so they are not re-attempted.
