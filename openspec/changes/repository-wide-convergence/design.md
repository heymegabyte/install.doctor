# Design

> **Architect:** codex
> **Architect Role:** assigned

## Coverage model

The tracked-file list is the source of truth. A deterministic audit assigns every path to one of: source, test, script, configuration, documentation, generated, encrypted, binary/media, vendored, or empty/sentinel. Each class has required validators. The final ledger must contain exactly one record for every `git ls-files` path and reject duplicates or omissions.

Semantic review is sharded by dependency closure rather than arbitrary file count. Repository summaries and OpenCode workers inspect bootstrap/home automation, aid/control-plane, site/docs, and repository/tooling/assets independently. The premium parent resolves conflicts, owns sensitive decisions, applies patches, and verifies the integrated tree.

## Decision policy

Findings are scored by impact, confidence, effort, risk, and reversibility. Implement automatically when evidence is high-confidence, the action is reversible, tests can prove it, and no external authority is needed. Record rather than implement speculative redesigns, destructive migrations, decoded-secret changes, or changes that conflict with project doctrine.

## File-class verification

- Source/scripts/config: parser, type, lint, schema, tests, call-site and dead-code analysis.
- Docs: link/reference accuracy, contradiction/staleness, spelling where reliable, and executable snippet validation.
- Generated: regenerate and compare; never hand-edit when a canonical generator exists.
- Encrypted: vault/header, filename, mode, and reference integrity only; never decrypt for this audit.
- Binary/media: magic type, extension agreement, dimensions/decodability, duplicate hash, reference/orphan analysis, and size thresholds.
- Empty/sentinel: explicit allowlist or defect.

## Convergence

Run the full inventory and validators, implement winners, rerun, then perform two consecutive independent finding passes. Convergence means neither pass produces a new actionable finding above the recorded threshold; it does not mean every file changes.

The approved 30-item program reopens convergence. Its implementation is dependency-ordered into five waves: (A) exploit and bootstrap safety; (B) secret, backup, and scheduler authority; (C) CI, catalog, and source provenance; (D) authenticated control-plane boundaries and observability; (E) consent, dependency modernization, and truthful documentation. A wave may proceed in parallel only across disjoint files and state; control-plane auth precedes state-changing or receipt endpoints, and independent recovery precedes destructive storage work.

## Cross-change ownership

`fleet-backup-recovery` owns Infisical authorization, backup-secret separation, scheduler reconciliation, ZFS discover/plan/apply/status, recovery escrow, restore evidence, and host rollout. This change owns repository enforcement and the remaining bootstrap, CI, control-plane, catalog, provenance, dependency, consent, and documentation work. `triad-convergence-langfuse-resilience` owns the Langfuse fail-open shell contract and Frontier-only OpenSpec authorship declaration; this change adds the mechanical verifier that prevents a non-Frontier author from passing validation.

Infisical is authoritative for operational secrets. Repository configuration stores references, not values. Local secrets are valid only for a declared machine-scoped offline/pre-network dependency and may never act as a silent general fallback. The independent recovery package is governed by `fleet-backup-recovery` and is not a second operational secret authority.

The approved Infisical program is enforced at repository boundaries as well as at runtime. `fleet-backup-recovery` owns I01–I30 behavior and host evidence. This change owns deterministic gates for manifest schema and immutability (I01–I06, I10), credential/reference leakage and CI federation (I07–I09, I13–I19, I24–I26, I29), authorization/telemetry/dashboard evidence (I11–I12, I22–I23, I27–I28), recovery-envelope provenance (I20–I21), and staged rollout receipts (I30). These gates consume redacted evidence and never require secret values in the repository.

Identity categories are non-substitutable: Cloudflare Access protects public human administration, GitHub/platform OIDC authenticates automation, Infisical workload identities authorize service secrets, Authentik is exceptional local/offline human access, and product-native auth owns customer accounts. A repository change that crosses these planes without a documented exception fails policy validation.

## Deterministic lazy-loading policy

Every installable catalog entry has a schema-validated `load_policy` and `load_rationale`. `lazy` is the default and requires no exception. Eager entries must use exactly one narrow class: `eager-bootstrap` for prerequisites required before the lazy resolver can work; `eager-supported-path` for a dependency inevitably exercised by a selected supported path; `eager-security-recovery` for security or recovery capability required before lazy infrastructure; or `eager-service` for an always-on service explicitly selected in the host's desired state. Eager entries also identify the consuming path, prerequisite, recovery obligation, or desired-state selector that justifies them. Popularity, convenience, historical preload status, optional integrations, and possible future use are not sufficient rationales.

Classification is deterministic from the versioned catalog, supported-path dependency graph, platform/role capability, and desired state. The same inputs produce the same ordered plan. Missing rationales, unknown classes, dependency cycles, eager services without explicit selection, and a lazy resolver that depends on an unavailable lazy package fail validation. Platform-specific entries may classify differently only through explicit platform/role overrides with their own rationale.

At runtime, interactive command discovery may install an eligible lazy package through the existing bounded, locked, provenance-checked path and then resume the original invocation. Noninteractive, privileged, offline, or policy-disabled contexts fail with an exact remediation rather than silently installing or partially configuring software. Supported workflows declare dependencies in advance so planning can install them as a transactional prerequisite. A failed lazy install leaves no success marker, duplicate task, service enablement, or ambiguous partial state; a later run can retry safely. Always-on services are never started merely because their package is discovered or installed.

Structured secret-free events record classification, reason code, trigger, platform/role, package, outcome, duration, fallback, and remediation. Metrics cover eager install count/time, shell/bootstrap startup budget, lazy cold/warm latency, failures, retries, offline fallbacks, and unused eager exceptions. Package names and bounded reason codes may be labels; commands, paths, errors, and run identifiers remain fields.

## Rollback

All mutations remain ordinary Git changes, grouped by subsystem with regression tests. No deploy or live-host mutation occurs. Generated outputs can be restored by their generator and removals remain recoverable from Git history.

## Install-routine convergence architecture

### Product goal and invariant

The install routine's goal is: **from one trusted command, converge any enrolled supported host from observed state to an explicit, reviewable desired state as quickly as safety permits, while remaining reproducible, resumable, reversible for installer-owned configuration, operable offline, and honest about every unsupported, skipped, pending, or failed outcome.** A beautiful terminal experience is a renderer of this engine, never a second execution path.

The canonical lifecycle is `discover -> validate -> plan -> approve -> apply -> verify -> record`. `status`, `resume`, and `rollback-config` consume the same schemas and journal. Interactive TUI, plain terminal, JSON/NDJSON, CI, and offline modes differ only in rendering and approval source. The authoritative desired state remains the portable `ENVIRONMENT.md` plus schema-validated catalog/host policy; observed facts and run evidence remain separate.

### Trust and release envelope

`https://app.install.doctor/start` is a minimal Bash stage-zero launcher. It creates a mode-0700 temporary directory under an allowed local filesystem, rejects symlinked/untrusted state, downloads an immutable release manifest with bounded HTTPS and zero redirects, and executes only verified local files. The schema-v3 envelope binds release ID, source commit, provisioner and engine URLs/sizes/SHA-256 values, exact Node runtime version, four macOS/Linux architecture runtime tuples, expiry, and signing-key ID. A repository-pinned SSHSIG public key verifies the manifest; checksum and exact-size verification then bind every selected artifact. Release publication independently validates the Node archives against a pinned upstream `SHASUMS256.txt`, detached signature, and release keyring before the Install Doctor signature is created. Missing verifier, signature, expected digest, immutable identity, size bound, or expiry fails closed with exact platform remediation. A deliberately named TLS-only development escape hatch is forbidden in CI, headless fleet enrollment, and production documentation.

The launcher never forwards arbitrary environment wholesale. It accepts an allowlist of nonsecret inputs, reads secrets through scoped runtime channels, scrubs inherited proxy/debug variables unless explicitly permitted, reconnects interactive input to `/dev/tty`, and uses `/dev/null` in noninteractive mode. Download retry, connect, total-time, and maximum-size bounds are explicit. A compatible system Node 22 or 24 may be reused; otherwise the provisioner re-verifies and extracts exactly one regular `bin/node` member from the launcher-staged signed Node 24 archive. Musl is rejected from the glibc runtime path. Root-to-user continuation uses an unpredictable root-owned directory whose sealed files remain non-writable through execution, with every digest rechecked in the target context. Temporary artifacts are removed on success, failure, signal, and handoff. The release manifest and verified hashes are retained in the run evidence without secret material.

### One engine, multiple renderers

The engine emits a versioned, append-only event protocol. Each event has bounded enums for lifecycle, phase, task, status, severity, platform, retry class, and lock domain; high-cardinality run IDs, paths, commands, durations, and redacted diagnostics are fields rather than labels. The TUI consumes the stream and shows global progress, dependency-aware task rows, per-worker identity, live interleaved output without line corruption, retry/backoff, elapsed time, current lock contention, skipped/blocked reasons, and a final evidence location. It supports resize, narrow terminals, keyboard-only navigation, reduced motion, `NO_COLOR`, log follow/filter, and detaching without cancelling the run. The plain renderer preserves the same information, while JSON/NDJSON remains stable for automation.

The production lifecycle core lives in the dedicated `packages/installer-engine` package. It may import only the narrow installer-contract export from the isolated `aid-core` foundation; it must not pull unrelated aid product behavior into bootstrap. Stage zero remains a minimal signed shell launcher until a verified self-contained engine artifact is present. During migration, `scripts/provision.sh` and `installx` are compatibility adapters, and B03 remains incomplete while either writes a competing plan/event stream or infers terminal success outside the engine.

TUI absence or renderer failure cannot stop the engine. Renderer backpressure is bounded and spills to protected local logs; execution never waits indefinitely for telemetry or display. The full terminal visual design requires a reviewable approved artifact before cosmetic implementation when the applicable design gate is activated, but engine and protocol work proceed independently.

### Typed dependency DAG and concurrency

Every mutation is a typed task node with stable ID, inputs digest, dependency IDs, capability predicates, check/plan/apply/verify operations, timeout, retry classification, resource estimate, privilege need, network need, consent class, lock domains, cleanup, and configuration compensation. Planning rejects cycles, unknown dependencies, duplicate IDs, missing capabilities, privilege/consent mismatches, and nodes that cannot be verified.

Ready nodes run through a bounded adaptive queue. Read-only discovery, verified downloads, compilation, and independent user-space changes may fan out. Package-manager transactions, repository metadata refreshes, privilege escalation, filesystem ownership changes, service-manager mutation, network enrollment, reboots, and each ZFS pool/dataset mutation use named exclusive locks and are serialized where their state overlaps. Concurrency defaults from CPU, memory, power, thermal, network, and environment class, respects a user ceiling, and decreases under pressure. Failure blocks dependents but permits unrelated safe branches according to the declared failure policy. Cancellation stops admission, terminates children with bounded grace, runs cleanup, writes a resumable journal, and never reports success.

Internal development work may use Claude, Codex, and OpenCode in parallel under the provider policy, but those agents do not become privileged bootstrap dependencies. OpenCode performs bounded throughput implementation after Frontier-authored OpenSpec; premium agents own decomposition, security decisions, integration, and final verification.

### Idempotency, resume, and rollback

Each task's check and verify operations are authoritative. A second unchanged run performs discovery and verification but produces no duplicate package transaction, identity, schedule, service transition, snapshot, marker, or configuration write. The plan digest binds release manifest, desired-state revision, normalized host facts, catalog/schema versions, task graph, and approved consents.

Before each task, the engine atomically journals `pending -> running`; after verification it records `verified`, `skipped`, `blocked`, or `failed` plus input/output digests. Resume revalidates the host identity, release and plan digests, previously verified postconditions, privilege/secret availability, and dependency closure. Changed or ambiguous state triggers re-plan; it never blindly skips a prior task because a marker exists. Only one apply/resume owns a host journal through an advisory lock with stale-owner detection.

Before installer-owned configuration or service-state mutation, the engine validates the candidate, captures the previous known-good bytes, metadata, and service enable/running state, writes atomically, then verifies. `rollback-config` walks the successful compensation records in reverse dependency order and restores only those assets. It does not uninstall packages, roll back OS updates, destroy user data, undo external side effects, or pretend every mutation is reversible. For those one-way operations, planning requires explicit consent and a recovery/runbook reference.

### Offline and degraded operation

An online `bundle create` operation produces a signed, content-addressed bundle containing the release manifest, engine, catalog, schemas, platform-specific artifacts, checksums/signatures, licenses, dependency graph, and a nonsecret inventory. It never embeds operational secrets. `bundle verify` succeeds before any mutation and rejects missing, extra, expired, wrong-platform, wrong-architecture, or unsigned artifacts. Offline planning reports exactly which selected capabilities are satisfiable; apply performs no network fallback. Secret-dependent tasks require an approved offline/pre-network secret class or remain blocked without weakening authority. Resuming online from an offline run re-plans against the new artifact set.

Production host-bound bundles use a two-phase request/sign/publish protocol; the target and ordinary CI runners never receive either the release private key or an offline-bundle private key. Discovery first emits a canonical, secret-free request containing a nonce, bounded validity, active release-manifest digest, desired-state revision, immutable host identity digest, normalized host facts and their digest, exact platform cell, selected dependency closure, normalized plan and operation-manifest digests, every canonical absolute target plus allowed mode/ownership class, and the complete artifact inventory. The requester authenticates with a short-lived claim-bound workload identity. The signing authority accepts only the repository, immutable workflow revision, protected production environment, event, ref, run attempt, release, and platform scopes declared by policy; a caller cannot broaden any field through workflow inputs or ambient environment.

Offline signing is a dedicated, non-building authority with a separate Ed25519 key. Its public key is trusted only through a release-root-signed, namespace-separated delegation that binds signer ID, public key, `install.doctor.offline-bundle` namespace, allowed release IDs/platform cells/artifact classes, maximum lifetime and size, and delegation validity/revocation epoch. The dedicated private key remains non-exportable or confined to the protected signer process and is never mounted in the builder, publisher, canary, target, logs, artifacts, or repository. Rotation overlaps public delegations only for a bounded interval; revocation prevents new signatures without making already-approved unexpired evidence unverifiable.

The authority independently fetches and verifies the signed release, reconstructs every artifact from immutable sources, parses the strict request, rediscovers policy-controlled catalog authority, reproduces the normalized plan from the supplied semantic inputs, verifies dependency closure and exact target containment, and rejects stale, replayed, cross-host, extra-artifact, mutable-URL, unapproved-path, or self-signed requests. It signs canonical manifest bytes only after validation, publishes the bundle to private immutable content-addressed storage with create-if-absent semantics, then emits a signed publication receipt binding request digest, delegation digest, manifest digest, storage object identity/ETag, requester claim digest, authority version, and timestamps. Host facts and paths are not placed in a public index; targets obtain a bounded single-object retrieval capability through the existing authorized delivery plane.

The same live host that produced the request downloads and executes the resulting bundle. Before mutation it re-discovers its protected machine identity and current semantic facts, reproduces the approved plan, compares every absolute target, and verifies the release root, signer delegation, bundle signature, content address, publication receipt, expiry, and one-time request nonce. A replaced ephemeral runner or changed host must request a new bundle. The canary's own report is not promotion authority: the evidence artifact is attested by the CI platform identity, and an independent promotion verifier re-fetches the immutable bundle, delegation, publication receipt, CI attestation, workflow/run conclusion, and committed engine journal before a platform cell may consume that evidence. A URL, archive checksum, locally generated key, workflow output, or `executionMode: offline` field alone never proves signed offline execution.

Native package and service mutation is a separate signed authority from generic catalog executables. The first admissible native closure is Debian `dpkg` plus systemd on an exact Linux distribution/version/architecture tuple. The release-signed catalog binds every `.deb` name, version, architecture, byte digest and size; repository origin/suite/component; verified metadata digest and signing-key fingerprint; dependency closure; affected conffiles and service units; and a maintainer-script policy. The offline bundle signer cannot invent or broaden that authority. Fedora/rpm, Alpine/apk, Arch/pacman, macOS/Homebrew, and every unproven manager remain explicitly unsupported until an equivalent signed repository/payload contract and disposable real-host receipt exist.

Offline native operations are strict typed package and service triples. They contain no caller-selected executable, argv, environment, hook, repository URL, manager flag, service name, or target path outside signed catalog authority. Package checks and verification require the exact installed name/version/architecture. Apply installs the complete verified dependency set inside one host-fenced native transaction from sealed descriptor-only payloads and never performs dependency resolution or network fallback. The transaction may use multiple fixed `dpkg` invocations when Debian `Pre-Depends` semantics require an admitted prerequisite to be configured before its dependent is unpacked; the signed relationship graph and installed-state observations determine that order, never caller input. Package mutation remains explicitly non-automatically-reversible: the receipt preserves prior signed payload references and exact forward-repair guidance, but the engine never silently removes, downgrades, or claims rollback.

The writable native path does not weaken the unprivileged read-only Bubblewrap sandbox. A distinct injected native runtime proves Linux, root authority, a disconnected network namespace, the exact host/package-manager tuple, and fixed root-owned non-symlink non-writable `gpgv`, `dpkg-query`, `dpkg-deb`, `dpkg`, and `systemctl` binaries before journal ownership or mutation. It independently proves the release-bound keyring, InRelease signature and parsed fields, signed Packages checksum entry, exact Packages stanza, `.deb` control metadata, and semantic dependency closure before root execution. The initial production profile admits packages with no maintainer scripts or triggers. A later package may be admitted only when every maintainer script/control member is bound by exact reviewed hashes and the receipt explicitly classifies its filesystem effects as broad and non-reversible; repository signing alone never implies a bounded mutation surface. Installation still uses a tested `policy-rc.d` service-start suppression policy, rejects direct service-manager invocation unless separately reviewed and declared, captures every declared affected service state before package configuration, and restores prior service state before explicit service tasks establish desired state. Package and service operations retain their named exclusive locks and dependency ordering.

Service-state mutation is independently reversible. Before `enable`/`disable` or `start`/`stop`, the engine durably captures the exact supported systemd state, applies through the fixed adapter, verifies the postcondition, restores on failure, and exposes the snapshot to reverse-dependency `rollback-config`. Ambiguous native states remain unsupported rather than coerced. Resume always rechecks package and service postconditions before replay. A manager is not promoted from unsupported by schemas or mocks: promotion requires a network-denied disposable host test proving clean apply, exact unchanged no-op, interruption/resume, service restoration, payload mutation resistance, and truthful non-reversible package failure evidence.

### Supported-platform contract

Support is capability-based and evidence-backed, not a blanket Unix claim. The manifest declares `verified`, `best-effort`, or `unsupported` per OS family, version range, architecture, environment class, role, init/service manager, filesystem, and package manager. Verified support requires a hermetic fixture plus periodic real-host/canary evidence for stage zero, plan, apply, unchanged reapply, interrupted resume, configuration rollback, and headless behavior. Initial verified targets are the repository's explicit fleet paths: macOS Intel/Apple Silicon, Ubuntu and Debian, Fedora, Arch, Alpine, WSL2 Ubuntu, Proxmox VE, Qubes dom0/AppVM, and containers, only at versions represented by current matrix fixtures. RHEL-compatible and OpenSUSE aliases remain best-effort until equivalent evidence exists. Native Windows and FreeBSD are unsupported by the Bash endpoint; PowerShell is a separate entrypoint and may be promoted only by the same evidence bar. Unknown versions fail planning unless an explicit best-effort override is recorded.

### Telemetry, privacy, and completion evidence

Every run writes protected local NDJSON events, a normalized plan, task journal, redacted logs, verification results, release provenance, duration/resource summaries, and a terminal receipt. Remote telemetry is consented, fail-open, bounded, batched, and scrubbed at source. It reports coarse platform/role, phase/task outcome, duration buckets, retry class, lock contention, rollback, resume, and unsupported reasons; it never sends secrets, command output, usernames, home paths, hostnames, arbitrary environment values, or file contents. Loki/metrics integrations consume the same event protocol with bounded labels. Telemetry outage cannot affect task results.

Completion means every selected node is `verified` or explicitly `inapplicable`; `skipped`, `blocked`, `pending-reboot`, `pending-verification`, and `failed` are not success. The terminal receipt includes exact next action and evidence paths. Claims about installation speed use measured cold/warm percentiles on named fixtures, not aspirational copy.

### Acceptance matrix

| Dimension | Required evidence |
|---|---|
| Trust | Tampered manifest, artifact, redirect, expiry, oversized response, missing verifier, and unknown key all fail before execution; valid pinned release succeeds. |
| Modes | TUI, plain, JSON/NDJSON, headless CI, and offline render the same normalized plan and terminal statuses. |
| DAG | Cycle/unknown dependency rejection; concurrency ceiling; exclusive lock proof; unrelated branch continuation; dependent blocking; cancellation cleanup. |
| Idempotency | Fresh apply succeeds; second unchanged apply records zero mutations; changed desired state mutates only its closure. |
| Resume | Forced interruption at every mutation boundary resumes safely; stale/foreign/tampered journal and changed host facts force re-plan. |
| Rollback | Invalid candidate auto-restores previous config; explicit reverse-order rollback restores bytes/modes/service state without touching live data. |
| Offline | Signed complete bundle applies with network denied; incomplete/wrong-platform/expired bundle fails before mutation; no hidden network fallback. |
| Platforms | Each `verified` matrix cell proves bootstrap, plan, apply, verify, unchanged reapply, interruption/resume, rollback, and headless mode; absent evidence downgrades the cell. |
| TUI | Concurrent output remains attributable and live; resize/narrow/NO_COLOR/reduced-motion/keyboard paths work; renderer crash leaves engine and evidence intact. |
| Security | Environment/secret allowlists, least privilege, untrusted state/symlink rejection, argv-safe execution, log redaction, and consent gates pass adversarial fixtures. |
| Operations | A failed task emits truthful terminal status, dependents are blocked, cleanup runs, remote telemetry timeout is fail-open, and the receipt gives exact recovery. |
| Performance | Stage-zero, time-to-plan, ready-queue utilization, critical path, cold/warm task latency, and peak CPU/memory/I/O are measured against versioned budgets per fixture. |
